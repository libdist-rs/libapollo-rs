Architectural changes (libmempool-rs -> libapollo-mempool)
----------------------------------------------------------
The in-tree `mempool/` crate replaces libmempool-rs, tuned
specifically for the leader-inlines-batch pattern used by all four
protocols here.

Key design choices:

1. `CachedBatch<Tx>` with `OnceLock`-cached batch hash. Populated
   eagerly during wire `Deserialize`, so follower-side
   `check_batch_hash` is a free `OnceLock` compare (was: re-serialize
   + SHA256 per incoming proposal).

2. `tx_hashes: Arc<[Hash<Tx>]>` also `OnceLock`-cached on `CachedBatch`.
   Computed lazily on first call and shared; `hydrate_tx_hashes` no
   longer recomputes per hydrate.

3. Mempool->consensus channel carries `(BatchHash, Arc<CachedBatch>)`
   directly. The leader's `do_propose` receives the Arc from the
   channel and skips the `read_batch().await` rocksdb round-trip
   that the libmempool integration forced.

4. `ProtocolMsg::NewProposal` / `NewBlock` / `Response` carry
   `Arc<CachedBatch<Transaction>>` instead of inline `Batch<Transaction>`.
   Serde-transparent Arc means the wire format is bit-identical to the
   inlined shape, but in-memory clones (e.g. when broadcasting) are
   Arc-bumps rather than deep copies of the payload.

5. No peer-to-peer mempool gossip. Every consensus protocol already
   inlines the batch in its proposal / response, so missing-batch
   recovery piggy-backs on the existing `ProtocolMsg::Request`
   paths. Drops the libmempool Synchronizer + mempool peer TCP.

6. `persist_batch` inserts into the in-memory `BatchCache` first,
   then enqueues a rocksdb write via `libstorage::Store::write`
   (which is itself a fire-and-forget mpsc send into the rocksdb
   writer task -- no disk-sync on the consensus critical path).
   A crashed node is faulty per our fault model (n > 2f), so a
   partial-persist batch is not a correctness concern: at least one
   honest follower that saw the proposal has the batch in its cache.

7. `read_batch` consults the `BatchCache` (DashMap-based, unbounded
   for benchmark) first and only falls through to rocksdb on
   eviction / out-of-window. A production LRU / round-GC goes
   here.

Notes on the regressions
------------------------
* **Apollo 7/3** (-30%) is a real regression, not noise. Apollo's
  chain-based client commit loop has been observed at ~5.5k tx/s
  across multiple runs (old baseline: 8k). Candidate causes: the
  extra follower-side `persist_batch` work (cache insert + rocksdb
  enqueue) on top of Apollo's already-heavy per-block processing,
  or the loss of the yield-point that the old code's
  `read_batch().await` in `do_propose` forced.

* **Sync HotStuff 3/1, 7/3** (-46%, -65%) show consistent regression
  of the same rough shape: followers pay `persist_batch` work per
  incoming proposal that wasn't present in the libmempool path's
  `on_commit`-only `read_batch`. Worth profiling.

* **Opt Sync 3/1** went from 169k -> 62k (-63%). The old 169k figure
  was an outlier: it was 2.4x the equivalent Sync HotStuff number
  and has never been reproduced on post-port measurements even with
  the libmempool code intact. Treat the 62k figure as the honest
  steady-state. Opt Sync 7/3 is within noise of old.

BFT checks preserved
--------------------
* `check_batch_hash` still runs on every incoming proposal -- the
  change is in cost (free `OnceLock` compare vs serialize + SHA256),
  not presence.
* All signature verifications, equivocation checks, certificate
  validation, and commit rules unchanged.
* Wire format for `ProtocolMsg` is bit-identical under
  serde-transparent `Arc` handling.

Notes on latency
----------------
Latency is end-to-end from client-side submit to client-side commit
observation. With `window=10000` in flight, latency is dominated by
queueing (a tx waits ~`window/throughput` seconds before being
batched). To measure raw commit latency, rerun with `-w 1` or a
window smaller than one block.

Follow-ups
----------
- Profile Sync HotStuff / Opt Sync under load to pin down the
  Apollo-7/3-style regression. Likely candidates: follower-side
  `persist_batch` cost, lost reactor yield-points, DashMap sharding
  under write pressure.
- Add proper LRU / round-scoped eviction to `BatchCache`.
- Consider a fast-path for the leader: `persist_batch` becomes a
  no-op when the Processor already installed the batch (it does,
  but `persist_batch` isn't called for leader-local batches
  currently -- verify and skip any redundant cache hit).
